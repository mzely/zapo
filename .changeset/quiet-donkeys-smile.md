Surface the raw `mediaretry` answer on `WaMediaRetryResult` and correct the reupload contract. The v1.8.0 notes stated that on `result: 'success'` only the `directPath` changes; in the field that does not always hold. Some primaries re-encrypt the file on every re-upload, so the answer is `success` with a fresh path but the re-served blob no longer matches the original `fileEncSha256` and `downloadBytes()` throws a MAC mismatch - two reuploads of the same message even return different ciphertext. Nothing in the round-trip carries key material for the new ciphertext (`messageSecret` is empty), so the message is unrecoverable through this API, and the docs now say so instead of promising the original key still works. To make that case diagnosable rather than invisible, a successful result now also carries `from` (the device that answered), `messageSecret` when the answer held a non-empty one, and `notification`, the whole decoded `MediaRetryNotification` including fields this version does not model. The `<error>` form of the notification keeps its previous three-field shape.
